# BMSG Universe 管理ページ 再設計案（2026-11-17）

状態：**画面構成の提案・実装前**。この文書の追加は開発ブランチのみ。現行のSETTINGSやDB、本番サイトは未変更。

## 目的・原則

- 小さいSETTINGSモーダルに編集機能が増殖する状態を解消。
- **SETTINGS → 管理 → 管理ページ（独立したフルページ）→ 各機能の専用ページ** を正規導線とする。
- 利用者の設定（ユーザー／推しメン／見た目／歌詞編集モード／カラオケお気に入り）はSETTINGSに残し、共通DBを変更する管理操作と分離。
- HOME / DATA / LABの下部ナビ、Universeの既存デザイン、ID・DB設計、主要ページのナビ動線を維持。
- 6つ程度の**業務別カテゴリ**を管理トップに表示。管理トップに編集フォームや大量の横タブを直接並べない。
- 一度に表示するのは１つの仕事・１つのフォーム。管理トップ／カテゴリ／編集という階層にし、各画面に「←管理」「←カテゴリ」とパンくずを表示。
- 新しい画面を作るために、同じGAS保存関数を複製しない。既存APIは維持し、UI・ルーティングのみ安全に移す。

## 画面仕様（スマホ優先）

### SETTINGS：小型モーダル

- 現在のアカウント・個人設定と、**『管理ページを開く』1行だけ**を表示する。
- 既存の管理画面リンク4つ（データ管理／プロフィール管理／画像管理／楽曲・歌詞管理）は切替成功後に撤去。入り口だけ先に消して機能喪失させない。
- パーソナル機能（歌詞編集モード・カラオケ推しセット）をDB管理へ移してしまわない。

### 管理トップ：フルページ

- 例：`管理 / MANAGEMENT` ヘッダー＋説明＋カテゴリ別カード（スマホ：1列、広い画面：2列）。
- 各カードはタイトル、目的、代表的操作２〜３項目、遷移矢印。**「開発中」「未実装」は非活性、押せるように見せない**。
- 普段の操作は上に配置。データ・保守は下部で区切る。
- 横５タブの小さな管理モーダルは廃止。機能ごとに必要なサブメニューだけ表示する。

### カテゴリ→編集画面

- `管理 › 楽曲・歌詞 › 既存曲を編集` のように、どこにいるか常時表示する。
- 検索・選択→編集→確認→保存の一方向。各画面で「←カテゴリに戻る」「管理トップへ戻る」が使える。
- 編集中の戻る／ブラウザ戻る／下部ナビは**未保存データの破棄確認**を通す。保存中は二重送信防止。
- スマホのセーフエリアを考慮したボタンサイズ（最小44px）、長いフォームは専用ページで縦スクロール。保存アクションはフォーム下部か下部固定。
- 成功時は同ページで値を再取得して成功通知。画面を勝手にSETTINGSへ戻さない。
- 背景、シアン／白アクセント、共通入力・カード・ボタンのデザインは`ManagementSystem.html`を継承。デザインの全刷新はしない。

## 技術設計（実装前の推奨）

1. 既存 `Router.html` / `AppCore.html` にルート `manage` を追加し、`navigateToWithParams('manage',{section:'songs',view:'edit',...})` などで階層を表す。深い階層はURL復元・ブラウザ戻るをテスト。
2. `ManagementHome.html`（新規）に**管理ページトップと共通パンくず／戻る操作**を実装。利用権限に応じて機能カードを表示する。
3. 既存の管理HTMLは、最初は壊さず流用。専用ページ用の表示部分を共通レイアウトへ段階移行する。旧モーダルを管理ページの中に更に重ねる設計は最終形にしない。
4. 現行の `ImageManagementEntry` / `ProfileManagementEntry` / `SongLyricsManagementEntry` / `CatalogManagementEntry` がSETTINGSに直接行を追加する構造は、導線の切替を確認してから廃止する。
5. 既存 `metrics` ルートは使い回す。現在の「戻る→HOME」などの動線を管理トップから開いた場合の戻り先に合わせる。計測中の離脱確認は維持。
6. UI権限と保存API権限は**両方**検証。現行`getCatalogManagementAccess`は管理者Googleメール許可制だが、他の保存APIには別のアクセスルールがある。入口を統合しただけで、既存利用者が編集不可にならないようにロールを確認する。
7. `ProfileManagementApi` / `CardApi`の固定グループ配列や、ユーザー個人設定と管理者権限の混同は別監査。新グループの反映と併せて対処。
8. 管理画面を新設しただけでDB側の旧シート同期停止、編集権限変更、旧タブ削除は実施しない。

## 実装フェーズ案（ユーザーに見せる挙動を極力変えず段階移行）

1. **ルートと管理ホームを先行実装**：既存SETTINGSに「管理ページ」入口を１つ追加。最初は新ページ内のカードから既存エディタを呼び出す。現行リンクは導線検証まで残す。
2. **カテゴリ単位で専用ページ化**：楽曲・歌詞、メンバー・プロフィール、グループ・ユニット、画像、計測の順に移す。保存関数は複製しない。
3. **不足の編集機能を追加**：グループ並べ替え／プロフィール項目編集／ゲスト修正／画像順などは優先度に応じて別タスク。
4. **回帰・権限・スマホ動作テスト**：全機能の登録・編集・保存／画面遷移／ブラウザ戻る／途中破棄／別ユーザーでの権限を確認。
5. **旧導線の撤去／旧入力シートの停止・廃止判断**：本番へ別途段階導入後、バックアップと依存関係監査を完了してから。

**非対象：この文書により本番デプロイ、DB編集、旧入力シート削除、新しいプロフィールクイズ復活は行わない。**

## 1. 画面階層の正本

**入口：`SETTINGS`（小さいモーダル）**
- `アカウント`：利用ユーザーの確認・変更
- `MY UNIVERSE`：推しメン、メンバーカラー表示、初期表示
- `LYRICS`：歌詞編集モード（歌詞ページ表示中）
- `KARAOKE`：推しセット（カラオケ用個人設定、歌詞ページ表示中）
- `ツール` → **`歌唱・センター秒数計測`**：既存`metrics`独立ページに遷移。管理へは移さない
- `管理` → **`管理ページを開く`**：この行だけ管理トップへ進む（権限あるユーザーだけ表示）

**管理トップ：`MANAGEMENT`（独立フルページ、route `manage`）**

```text
SETTINGS
 ├─ アカウント
 ├─ MY UNIVERSE
 ├─ 歌詞編集／カラオケの個人設定
 ├─ ツール → 歌唱・センター秒数計測 [別ページ：manageと無関係]
 └─ 管理 → 管理ページを開く
       ↓
    MANAGEMENT （管理トップ／フルページ）
     ├─ ① 楽曲・歌詞
     │    ├─ 楽曲を追加
     │    ├─ 楽曲を編集
     │    └─ 歌詞のゲストを管理 ※
     ├─ ② メンバー・プロフィール
     │    ├─ メンバーを追加
     │    ├─ メンバーを編集
     │    ├─ プロフィールを編集
     │    └─ プロフィール項目を管理
     ├─ ③ グループ・ユニット
     │    ├─ グループ・ユニットを追加
     │    ├─ グループ・ユニットを編集
     │    └─ ユニットの所属を編集
     ├─ ④ メンバー画像
     │    ├─ 画像を登録・差し替え
     │    └─ 画像の表示設定 ※

          ├─ DBを点検

          └─ バックアップ・移行管理 ※
```

※ 今後追加予定。**未実装項目は公開まで非表示または明確に操作不可。** 空のページやダミーボタンは出さない。

上の階層は**「管理トップ → カテゴリページ → 操作画面」まで**。操作画面で対象選択やサブセクションを展開し、必要以上にページ階層を増やさない。

## 2. 管理カテゴリ・項目名・機能の詳細

### ① 楽曲・歌詞

カテゴリ紹介：**「曲の登録、クレジット、歌詞・歌割りを編集」**

| 管理ページの表示名 | 押した先でできること | 実装状態と設計 |
|---|---|---|
| **楽曲を追加** | 曲名、アーティスト、初回リリース日、発売形態、収録作品、タイトル曲、作詞・作曲・振付、歌詞を登録 | 既存SongLyricsManagementで「歌詞あり」を実装。開発版では「歌詞なし」登録も実装。**入口は1つに統合**し、途中で「歌詞を追加する／後で追加」を選ばせる |
| **楽曲を編集** | 曲を検索→曲情報／クレジット／歌詞・歌割り／歌唱者／ソロ分類を編集。必要なら最後に楽曲削除 | 既存SongLyricsManagementと開発版Catalogの機能を分割せずに集約。削除は編集画面下部の危険操作、確認と参照チェック必須 |
| **歌詞のゲストを管理** ※ | ゲスト名を確認・修正、未使用ゲストを削除 | 既存歌詞解析時の新規Guest登録は流用。変更・削除の必要性を確認してから追加 |

**名称を避けるもの**：「楽曲マスター」「歌詞DB」「クレジット登録専用画面」。ユーザーが何をしたいかを前面に出す。

### ② メンバー・プロフィール

カテゴリ紹介：**「メンバーの登録とプロフィールを管理」**

| 表示名 | できること | 実装状態と設計 |
|---|---|---|
| **メンバーを追加** | 名前、主所属グループ、メンバーカラー、初期プロフィール・所属行をまとめて登録 | 開発版Catalog。カラーコードはグループ／メンバー横断で重複拒否 |
| **メンバーを編集** | 名前・カラー変更、主所属変更、メンバーの表示順変更。対象を選択した後に安全な削除 | 開発版CatalogとCatalogMemberMaintenance。削除は依存チェック＋強い確認、初期状態は実行不可 |
| **プロフィールを編集** | メンバーを選択して、誕生日・血液型など登録済み項目の内容を編集 | 既存ProfileManagementを利用。メンバーの新規登録機能とは分離 |
| **プロフィール項目を管理** | 新項目の追加、非表示・再表示。**将来**項目名・分類（基本／好み等）・表示順を編集 | 開発版ProfileFieldManagement。既存値は非表示でも保持。型の変更はデータ破損リスクがあるため通常編集UIに設けない |

**区別する言葉**：「プロフィールを編集」=メンバーの回答・値。「プロフィール項目を管理」=質問・欄の定義。これで似た名前の重複を防ぐ。廃止済みプロフィールクイズの設定は置かない。

### ③ グループ・ユニット

カテゴリ紹介：**「グループの基本情報とユニットの所属を管理」**

| 表示名 | できること | 実装状態と設計 |
|---|---|---|
| **グループ・ユニットを追加** | 名前、グループかユニットかの種別、カラー、表示順（初期自動） | 開発版Catalog |
| **グループ・ユニットを編集** | 名前・カラーの変更。**将来**表示順変更と参照ゼロの場合の安全削除 | 開発版Catalog、並び替え・削除は追加予定。データ参照が残る名称変更は制限 |
| **ユニットの所属を編集** | ユニットを選択→所属メンバー一覧→追加／除外／上下並べ替え | 開発版CatalogUnitMembership。**主所属は変えず、他ユニットに影響しない** |

「所属」は曖昧になりやすいので、**メンバーの主所属変更は②「メンバーを編集」**、複数ユニットへの参加は③「ユニットの所属を編集」に固定。

### ④ メンバー画像

カテゴリ紹介：**「プロフィールやトレカで使う画像を設定」**

| 表示名 | できること | 実装状態と設計 |
|---|---|---|
| **画像を登録・差し替え** | メンバー選択、レアリティ選択、画像アップロード／確認して差し替え、欠落画像の修復 | 既存ImageManagementを流用 |
| **画像の表示設定** ※ | 画像の表示順やプロフィールのメイン画像の指定。未使用画像の安全な削除を含むかは要確認 | 未実装／今後必要なら追加 |

「トレカ管理」はユーザーの**カード所持履歴の編集**と誤解されやすいので使わない。正式なカテゴリ名は**メンバー画像**。

### ⑤ データ点検・保守 ［高度な管理者限定］

カテゴリ紹介：**「データの異常・変更履歴・移行状態を確認」**

| 表示名 | できること | 実装状態と設計 |
|---|---|---|
| **DBを点検** | IDの重複、孤児参照、歌詞の順序、クレジットの整合性などを**読み取り専用**で検査 | 開発版CatalogDbAudit |
| **変更履歴を見る** ※ | 操作した人、対象、日時、変更内容を確認 | Auditログあり。専用UIは今後 |
| **バックアップ・移行管理** ※ | 旧入力シート停止前の確認、バックアップ・DBスキーマ移行の事前チェック | 開発版Catalogのスキーマ移行処理を一般編集画面から隔離。管理者のみ・危険操作確認必須 |

「データ管理」という曖昧な名前は**カテゴリ名には使わない**（管理トップ全体の意味とかぶるため）。通常の管理トップではこの保守カテゴリを一番下に離して表示。

## 3. 主要画面のUIと戻る動線

### SETTINGS
- スマホの小型モーダルのまま。保存フォームは追加しない。
- 管理リンクは**「管理ページを開く」1つ**。
- **「歌唱・センター秒数計測」は引き続き「ツール」**の独立リンク。管理画面から重複表示しない。
- 設定が終わったらモーダルを閉じ、管理ページに入る時だけフルページ遷移。

### 管理トップ（フルページ）
- 上部タイトル：`MANAGEMENT`／「管理ページ」。
- 4つの主カテゴリカード：**楽曲・歌詞／メンバー・プロフィール／グループ・ユニット／メンバー画像**。
- 下部に管理者限定の「データ点検・保守」。

- 未実装項目を偽のリンクにしない。カードの表示も適切な保存権限で制御。

### カテゴリページ
- タイトル＋説明＋2～4個の操作（縦に並ぶ選択行）。
- 例えば**「メンバー・プロフィール」→「メンバーを編集」**に進む。
- 必要ならカテゴリ内から「管理トップに戻る」。古い5タブの管理モーダルを新しい画面へ重ねない。

### 操作ページ
- タイトル例：「楽曲を編集」。
- 最上部に`管理ページ › 楽曲・歌詞 › 楽曲を編集`パンくず。スマホは1行＋戻るアイコン。
- 対象の検索・選択 → フォーム → 保存。関連操作は同一ページ内でタブ/アコーディオンを使うが階層は増やさない。
- 名前・カラー等の重複検証と、保存後の再取得を継続。
- 削除は対象詳細の最下部に「削除する」＋影響確認ダイアログ。**管理トップには「削除」カードを置かない**。
- 戻る・ブラウザの戻る・下部ナビを使う際に未保存変更があれば破棄確認。保存中は二重送信を防止。
- 44px以上のタップ対象、セーフエリア、スマホの縦スクロールに対応。共通`ManagementSystem.html`とUniverseデザインを流用。

## 4. 技術設計（実装の境界）

- `ROUTES.manage`と管理ホーム表示を`AppCore.html`／`Router.html`に追加する構想。`page=manage&section=songs&action=edit`などで階層を維持。ブラウザ戻る・URL再表示もテスト。
- ユーザーの基本ルート（HOME／DATA／LAB）や既存`metrics`の機能・戻る確認は変更しない。`metrics`の現在の戻り先はHOME。管理ページに戻す処理は追加しない。
- 既存の`CatalogManagement.html`、`SongLyricsManagement.html`、`ProfileManagement.html`、`ImageManagement.html`を、機能実装を壊さない形でページ表示に段階移行。保存APIを**重複実装しない**。
- 現在4つのEntryがSETTINGSへ直接管理リンクを足している。**新ルートでアクセスできることをテストしてから**4つのリンクを1つに統合する。
- Category単位の導線と、保存APIの**権限は別**に検証する。Googleログインの管理者制限を迂回させないし、既存利用者が急に編集不可になるのも避ける。
- 新グループがProfile/Card等へ反映されるよう、固定グループリストは別のP0改修対象。
- 管理ページのために`12_Videos`や`13_VideoSegments`を再作成しない。動画分析の再開は別プロジェクトの決定として管理する。
- 旧入力タブの停止・削除は別工程。本ドキュメントは管理ページの仕様を確定する**設計更新**であり、機能導入そのものではない。

## 5. 段階的な実装順（UIの安全な移動）

1. **共通管理ルート＋管理トップ**：SETTINGSへ入口を1つ追加。旧4リンクは新導線をテストするまで一時残す。
2. **4カテゴリに既存編集を整理**：楽曲・歌詞 → メンバー・プロフィール → グループ・ユニット → メンバー画像の順。操作画面をフルページ化、保存関数と共通デザインを流用。
3. **保守メニューを分離**：DB診断・スキーマ移行を通常編集から隔離する。
4. **不足操作を追加**：グループ表示順、プロフィール項目名・分類・表示順、必要ならゲスト訂正や画像表示設定。型変更・削除は別の安全設計が必要。
5. **回帰／権限／スマホの試験**：実App ScriptとCore/Logの複製を使って動線・保存・戻る・更新・未保存警告を検証。
6. **切替**：問題なく動く場合だけ旧モーダルの管理リンクを撤去。DB旧入力操作と直接編集権限の切替は別工程。
